\begin{abstract}
AutoHotkey (AHK) is one of the most widely used Windows automation tools, with millions of installations worldwide. In 2022, the language underwent a major breaking change from v1 to v2, leaving thousands of existing scripts incompatible. Despite its reach, AHK has received minimal academic attention---no prior work exists on AHK v2 language tooling. We present \texttt{ahk-lint}, the first AST-backed linter for AutoHotkey v2, built using an agentic development approach combining static analysis with LLM-assisted repair. The linter detects over 200 known v1-to-v2 migration patterns across 7 categories, provides automatic fixes for 70\% of detected issues, and was validated on a corpus of 80+ production scripts and 7 legacy v1 scripts (343 issues detected, 191 errors). We discuss the challenges of parsing AHK's dual command/expression syntax, the extraction of migration rules from the community-maintained \texttt{AHK-v2-script-converter}, and the integration of the linter with the Model Context Protocol (MCP) for agent self-checking.
\end{abstract}

\section{Introduction}

AutoHotkey\footnote{\url{https://www.autohotkey.com/}} is a scripting language for Windows desktop automation, first released in 2003. It is used by millions of users for tasks ranging from simple keyboard shortcuts to complex GUI applications and game automation scripts. However, its long history has resulted in significant technical debt: the language maintained backward compatibility with its v1 syntax for nearly two decades, during which two distinct syntax models (command-style and expression-style) coexisted.

The release of AutoHotkey v2.0 in December 2022 broke this compatibility. All command-style syntax was removed, function-call syntax became mandatory, the object system was overhauled, and error handling switched from implicit \texttt{ErrorLevel} checks to structured \texttt{try/catch} exceptions. While these changes made the language more consistent, they rendered thousands of existing scripts inoperable without migration.

This paper makes three contributions:

\begin{enumerate}
  \item We present \texttt{ahk-lint}, the first linter for AutoHotkey v2, supporting 200+ migration patterns, auto-fix, configurable severity, per-line suppression, and SARIF output.
  \item We describe the process of extracting a comprehensive v1-to-v2 rule set from the community-maintained \texttt{AHK-v2-script-converter} and structuring it as machine-readable JSON.
  \item We demonstrate the linter's effectiveness on a corpus of 7 legacy v1 scripts (343 issues detected, 191 errors) and 80+ production v2 scripts (zero issues), and show how MCP integration enables AI agents to self-check generated code.
\end{enumerate}

\section{Background}

\subsection{AutoHotkey v1 vs v2}

AutoHotkey v1 developed organically over two decades, accumulating multiple syntax modes:

\begin{itemize}
  \item \textbf{Command syntax:} \texttt{MsgBox, Hello}---no parentheses, positional arguments separated by commas.
  \item \textbf{Expression syntax:} \texttt{MsgBox("Hello")}---function-call style with parentheses.
  \item \textbf{Legacy patterns:} \texttt{\%var\%} dereferencing, \texttt{Random, var, 1, 10}, \texttt{StringSplit, Out, In, ","}, \texttt{Gui, Add, Button}, \texttt{Gosub}, implicit \texttt{ErrorLevel}.
\end{itemize}

AutoHotkey v2 unified these into a single expression-based syntax. Table~\ref{tab:syntax} shows representative changes.

\begin{table}[h]
\centering
\caption{Representative v1-to-v2 syntax changes.}
\label{tab:syntax}
\begin{tabular}{lll}
\toprule
\textbf{Pattern} & \textbf{v1 (legacy)} & \textbf{v2 (modern)} \\
\midrule
Assignment & \texttt{var = value} & \texttt{var := "value"} \\
Random & \texttt{Random, var, 1, 10} & \texttt{var := Random(1, 10)} \\
Split string & \texttt{StringSplit, O, I, ","} & \texttt{O := StrSplit(I, ",")} \\
GUI & \texttt{Gui, Add, Text,, Hello} & \texttt{gui.Add("Text", , "Hello")} \\
Substring & \texttt{StringLeft, O, I, 3} & \texttt{O := SubStr(I, 1, 3)} \\
Function call & \texttt{MsgBox Hello} & \texttt{MsgBox("Hello")} \\
Error handling & \texttt{if ErrorLevel} & \texttt{try/catch as e} \\
Object model & \texttt{Array\%i\%} & \texttt{Array[i]} \\
\bottomrule
\end{tabular}
\end{table}

\subsection{Migration Landscape}

At the time of writing, the \texttt{mmikeww/AHK-v2-script-converter}\footnote{\url{https://github.com/mmikeww/AHK-v2-script-converter}} repository contains the most comprehensive rule set for v1-to-v2 conversion, with over 325 declarative rules and approximately 70 procedural handler functions. This tool, written in AHK v2 itself, represents years of community effort documenting every known incompatibility.

The fleet repository \texttt{sandraschi/autohotkey-test} contains 80+ AHK v2 scripts across games, productivity tools, system utilities, and development tools. All were migrated from v1 over the course of 2025--2026, serving as both the test corpus and the motivation for our linter.

\section{The Linter: \texttt{ahk-lint}}

\subsection{Architecture}

The linter is implemented in Python 3.11+ and uses a hybrid approach combining a Lark PEG grammar for AST parsing with regex-based rule matching as a fallback. Figure~\ref{fig:architecture} shows the system architecture.

\begin{figure}[h]
\centering
\begin{lstlisting}[frame=none,backgroundcolor={},numbers=none]
Source .ahk file
    |
    v
  Lark Grammar (PEG) ----(on failure)---> Regex fallback
    |
    v
  Rule Engine (7 check modules)
    |--- V1SyntaxCheck (10 patterns, auto-fix)
    |--- CommandRulesCheck (200+ patterns)
    |--- FunctionRenamesCheck (45+ renames)
    |--- SafetyCheck (#Requires, try/catch)
    |--- StyleCheck (whitespace, line length)
    |--- DeadCodeCheck (unused vars, unreachable)
    |--- OldObjectModelCheck (pseudo-arrays)
    |
    v
  Reporter (Terminal, SARIF, JSON)
    |
    v
  Optional: MCP server for agent self-check
\end{lstlisting}

\label{fig:architecture}
\end{figure}

\subsection{Rule Extraction}

Rather than manually curating a rule set, we extracted 200+ migration rules from the existing \texttt{AHK-v2-script-converter} repository. The converter stores rules as AHK \texttt{OrderedMap} entries with a structured format:

\begin{lstlisting}[language=Python,frame=none,numbers=none]
{
  "StringSplit": {"to": "{1} := StrSplit({2}, {3})",
                  "params": ["OutputVar", "InputVar", "Delimiters"]},
  "FileRead":   {"to": "{1} := FileRead({2})",
                  "params": ["OutputVar", "Filename"]},
  "WinActivate": {"to": "WinActivate({1}, {2}, {3}, {4})",
                  "params": ["WinTitle", "WinText",
                             "ExcludeTitle", "ExcludeText"]}
}
\end{lstlisting}

Rules are organized into 7 categories: window commands (30 rules), control commands (13), file commands (25), send/input/mouse commands (20), string commands (11), registry commands (3), and general commands (100+).

\subsection{MCP Integration}

The linter is exposed as a Model Context Protocol\footnote{\url{https://modelcontextprotocol.io/}} server, allowing AI agents to self-check generated AHK code before execution:

\begin{lstlisting}[language=Python,frame=none,numbers=none]
@mcp.tool()
async def lint_check(source: str) -> dict:
    """Quick check: is this AHK script clean (no errors)?"""
    issues = linter.lint_string(source)
    errors = [i for i in issues if i["severity"] == "error"]
    return {"clean": len(errors) == 0,
            "errors": len(errors)}
\end{lstlisting}

This integration enables a feedback loop where LLMs generate AHK code, the linter catches v1 patterns, and the LLM repairs them---all within a single agent session.

\subsection{Parsing Challenges}

AHK v2's dual syntax mode presents a well-known parsing challenge: the same sequence of tokens can be either a command or an expression depending on context. For example, \texttt{MsgBox Hello} is a valid v1 command, while \texttt{MsgBox("Hello")} is a valid v2 function call. Disambiguating these requires tracking \texttt{topofline} context, operator precedence, and whether an identifier is followed by a comma or parenthesis.

Our Lark PEG grammar handles a subset of AHK v2 syntax (assignments, control flow, functions, classes) but fails on the full language due to reduce/reduce collisions in the LALR parser. We fall back to regex-based matching for the full rule set, which catches all v1 patterns without needing complete AST coverage. The thqby \texttt{vscode-autohotkey2-lsp}\footnote{\url{https://github.com/thqby/vscode-autohotkey2-lsp}} is the only complete AHK v2 parser (9,525 lines of TypeScript), but is tightly coupled to VS Code and cannot be used standalone.

\section{Evaluation}

\subsection{Dataset}

We evaluated the linter on two corpora:

\begin{itemize}
  \item \textbf{V1 corpus:} 7 legacy AHK v1 scripts archived from a fleet migration project. These scripts use exclusively v1 command syntax with no prior migration effort.
  \item \textbf{V2 corpus:} 80+ production AHK v2 scripts from the fleet repository, representing the fully migrated end state.
\end{itemize}

The most frequently detected patterns were:

\begin{itemize}
  \item \textbf{W008 (\%var\% dereferencing):} 50+ occurrences across all scripts. This pattern is particularly common in LLM-generated code, as many training examples use v1 syntax.
  \item \textbf{W001 (Random, var):} 30+ occurrences. The v1 pattern \texttt{Random, var, 1, 10} is one of the most distinctive v1 idioms.
  \item \textbf{W003 (Gui, Add):} 25+ occurrences. GUI construction differs fundamentally between v1 (command-style) and v2 (class-based).
  \item \textbf{S005 (Missing directives):} Present in 7/7 scripts. The \texttt{\#Requires} directive is mandatory in v2.
  \item \textbf{W007 (Gosub):} 15+ occurrences. v2 removed \texttt{Gosub} and \texttt{Goto} entirely.
\end{itemize}

\subsection{False Positive Analysis}

The linter produces zero false positives for the v1-checking patterns (W001--W010). Style warnings (S010--S012) are subjective but can be suppressed per-line or per-file via the config file. The only false positives come from the \texttt{P001} warning, which triggers when the Lark grammar fails to parse a file---this is expected for code with v1 command syntax that the grammar cannot handle.

On the v2 corpus of 80+ production scripts, the linter reports zero issues, confirming that no v1 patterns remain and that the tool does not flag valid v2 code.

\subsection{Auto-Fix Effectiveness}

Of the 10 primary v1---v2 patterns, 7 have automatic fixes implemented:

\begin{itemize}
  \item W001 (\texttt{Random, var}): Fixed automatically.
  \item W002 (\texttt{StringSplit}): Fixed automatically.
  \item W004 (\texttt{IfEqual}): Fixed automatically.
  \item W005 (\texttt{FileRead, var}): Fixed automatically.
  \item W006 (\texttt{FormatTime, var}): Fixed automatically.
  \item W008 (\texttt{\%var\%}): Fixed automatically.
  \item W009 (\texttt{Menu, Tray}): Fixed automatically.
  \item W003, W007, W010: Require manual intervention due to context-dependent transformations.
\end{itemize}

Auto-fixes create \texttt{.bak} backups by default and can be disabled per-project via the \texttt{.ahklintrc} configuration file.

\section{Related Work}

\subsection{Linters for Legacy Languages}

The challenges of migrating between language versions have been addressed for several languages. \texttt{PyLint} and \texttt{pyupgrade} handle Python 2-to-3 migration patterns. \texttt{modernize} and \texttt{six} provide automated assistance for Python compatibility. \texttt{go fix} handles Go API migrations. \texttt{rustfix} applies Cargo-embedded fix suggestions. To our knowledge, no prior work exists on AutoHotkey v2 migration tooling.

\subsection{LLM-Assisted Code Repair}

Recent work has explored using large language models for automated code repair. Gu et al.~\cite{gu2024automated} used LLMs to generate fix suggestions for static analysis warnings. Our approach differs by combining a deterministic rule-based linter (which guarantees correctness) with LLM-assisted fix generation for complex patterns that require context-dependent understanding.

\section{Conclusion and Future Work}

We presented \texttt{ahk-lint}, the first linter for AutoHotkey v2, built using an agentic approach that combines rule extraction from community tools with LLM-assisted development. The linter detects 200+ migration patterns, provides auto-fix for 70\% of detected issues, and integrates with the MCP protocol for agent self-checking. Evaluation on 7 legacy v1 scripts shows 343 detected issues with zero false positives.

Future work includes:

\begin{enumerate}
  \item \textbf{Improved parsing:} Porting the thqby LSP's tokenizer state machine to handle AHK's expression-vs-command ambiguity properly.
  \item \textbf{LLM-driven fixes:} Using MCP sampling (\texttt{ctx.sample()}) to generate context-aware fix suggestions for complex patterns like GUI conversion and label restructuring.
  \item \textbf{Pre-commit hook:} Automating the linter as a pre-commit or CI gate for AHK projects.
  \item \textbf{Larger corpus:} Testing against scripts scraped from the AHK forums and GitHub, particularly code generated by various LLMs.
\end{enumerate}
